# Настройка СКД `MON_МониторЗакупокЭксперимент`

Отчет использует внешний набор данных-объект.

Модуль объекта отчета:

```text
МОДУЛЬ_ОБЪЕКТА_ОТЧЕТА_ЗАКУПОК_ЭКСПЕРИМЕНТ.txt
```

Имя объекта, содержащего данные:

```text
МониторЗакупок
```

## 1. Набор данных

Вкладка `Наборы данных`.

Создать набор данных типа `Объект`.

Рекомендуемое имя набора:

```text
НД_МониторЗакупок
```

Внизу указать:

```text
Имя объекта, содержащего данные = МониторЗакупок
```

Параметры набора данных не заполнять. Параметр `ДатаОтчета` задается на вкладке `Параметры` схемы компоновки.

- `Путь` = то же имя;
- `Роль` не заполнять;
- ограничения доступа не ставить;

`ЦенаСредняя` нельзя считать как `Максимум(ЦенаСредняя)` и нежелательно считать как обычное вычисляемое поле строки. На группировках это даст максимум или среднее из строковых цен, а не взвешенную цену остатка. Правильная формула всегда должна делить агрегированную сумму рублей на агрегированное количество с ценой.

Если интерфейс не дает сразу ввести выражение для `ЦенаСредняя`, порядок такой:

1. Добавить поле `ЦенаСредняя` на вкладке `Наборы данных`.
2. Перенести `ЦенаСредняя` в ресурсы.
3. В строке ресурса заменить выражение агрегации на:

```text
Окр(ВЫБОР КОГДА Сумма(КоличествоСЦеной) = 0 ТОГДА 0 ИНАЧЕ Сумма(СтоимостьРуб) / Сумма(КоличествоСЦеной) КОНЕЦ, 2)
```

Если заменить выражение невозможно, `ЦенаСредняя` лучше временно убрать из ресурсов и оставить только `ОстатокРуб` + `ОстатокСЦеной`; неверную среднюю цену в отчете лучше не показывать.

## 5. Настройки варианта отчета

Вкладка `Настройки`.

Создать вариант:

```text

```

Структура отчета:

```text
Отчет
  КонтурБизнеса
    ОрганизацияНормы
      КатегорияНормы
        СкладНаименование
          НоменклатураНаименование
```

Для первой проверки можно остановиться на:

```text
Отчет
  КонтурБизнеса
    ОрганизацияНормы
      КатегорияНормы
```

Важно: `ТипЕдиницыКонтроля` - это поле группировки, а не параметр и не ресурс. Его нужно добавить только на вкладке `Наборы данных` как обычное строковое поле, после чего оно появится в доступных полях настроек отчета. В ресурсы его добавлять не нужно.

Для сверки единиц измерения лучше временно использовать такую структуру:

```text
Отчет
  КонтурБизнеса
    ОрганизацияНормы
      ТипЕдиницыКонтроля
        КатегорияНормы
```

Если ресурс `ТипЕдиницыКонтроля` уже добавлен с агрегацией `Количество(...)`, его лучше удалить из ресурсов. Он не нужен для сумм и будет только путать отчет.

## 11. Вариант `ПрофильСезонности`

Это первый слой для физичного расчета нормы. Он не считает норму напрямую, а показывает сезонный профиль фактического потребления по месяцам.

Отбор:

```text
СлойДанных = ПрофильСезонности
```

Структура:

```text
Отчет
  КонтурБизнеса
    ОрганизацияНормы
      ТипЕдиницыКонтроля
        КатегорияНормы
          МесяцСпроса
```

Выбранные поля:

```text
КатегорияНормы
МесяцСпроса
СпросМесяцаКг
СпросМесяцаУслЕд
ДоляГодовогоСпроса
ИндексСезонности
СезонныйПик
СтатусСезонности
```

Смысл:

```text
ИндексСезонности = спрос месяца / средний месячный спрос за 12 месяцев
```

Если индекс сильно выше 1, категория имеет пик. Если активных месяцев мало, это не обычная оборачиваемость, а сезонное окно. Этот слой нужен, чтобы заменить коэффициенты закупщиков реальным календарем спроса.

Важно по периоду: дата отчета и окно нормы разделены. Дата отчета управляет срезом остатков, а спрос для нормы и сезонности берется с `01.01.2025` по последний полностью закрытый месяц, найденный в данных спроса. Если последние движения есть `13.04.2026`, то апрель не включается, а окно нормы становится `01.01.2025-31.03.2026`. Поэтому отчет на `30.06.2025`, `30.09.2025`, `30.11.2025` или `31.03.2026` должен менять остатки, но не должен менять сам принцип расчета нормы.

## 12. Вариант `СводСезонности`

Это рабочий короткий слой для следующего шага нормы. Он сжимает помесячный профиль до одной строки на категорию.

Отбор:

```text

```

Структура:

```text

    ОрганизацияНормы
      ТипЕдиницыКонтроля

          КатегорияНормы
```

Выбранные поля:

```text

СпросВМесяцКг
СпросВМесяцУслЕд
МесяцевВПериодеСпроса
АктивныхМесяцевСпроса
МаксимальныйИндексСезонности
ДоляСпросаВКонтуре
КлассЗначимостиСпроса
МесяцыПиковСезонности
СтатусСезонности
```

Смысл `ТипПолитики` здесь расчетный, а не заданный по названию. Он выводится из фактического профиля спроса:

```text
Выраженное сезонное окно -> Сезонная
Сжатый сезон / выраженные пики -> Партийная/сезонная
Регулярный спрос с пиками -> Обычная/пиковая
Регулярный спрос с умеренными пиками -> Обычная/пиковая
Ровный спрос при 10+ активных месяцах -> Обычная
Хвостовой спрос -> Проверить/хвост
Малый нерегулярный спрос -> Партийная/малая
Остальное -> Партийная/неровная
```

`ДоляСпросаВКонтуре` нужна, чтобы высокий индекс сезонности у маленьких хвостовых категорий не превращался в ложную сезонность. Классы значимости:

```text
Ключевая >= 15% спроса контура/единицы
Значимая >= 3%
Малая >= 0,5%
Хвост < 0,5%
```

Если категория потребляется почти каждый месяц, высокий пик не считается сезонным окном. Такая строка получает `Обычная/пиковая`: для нее базовая норма считается как регулярная, а пик должен влиять на страховой запас и ширину коридора.

## 14. Вариант `БазаНормы`

Это первый расчетный слой `min / target / max`. Он соединяет:

```text
СводСезонности -> спрос, пики, тип политики
ПрофильПоставок -> период пополнения, партия, класс поставки
```

Важное ограничение: срок поставки пока не известен из данных, поэтому `СрокПоставкиДней = 0`, а статус будет `Черновик без срока поставки`. Это не финальная норма, а физическая база для обсуждения с закупками.

Отбор:

```text
СлойДанных = БазаНормы
```

Структура:

```text
Отчет
  КонтурБизнеса
    ОрганизацияНормы
      ТипЕдиницыКонтроля
        ТипПолитики
          КлассПоставки
            КатегорияНормы
```

Выбранные поля:

```text
КатегорияНормы
ТипПолитики
КлассПоставки
СпросВМесяцКг
СпросВМесяцУслЕд
СпросВДень
ПериодПополненияДней
СтраховойЗапасДней
ПиковыйБуферКг
ПиковыйБуферУслЕд
МинимальнаяПартия
БуферПоставки
НормаМинКг
НормаЦельКг
НормаМаксКг
НормаМинУслЕд
НормаЦельУслЕд
НормаМаксУслЕд
СтатусРасчетаНормы
КомментарийНормы
```

Формула:

```text
СпросВДень = Окр(СпросВМесяц / 30, 2)
ПериодПополненияДней = МесяцевВПериодеСпроса * 30 / МесяцевСПоставками
СтраховойЗапасДней = операционный буфер по типу политики
ПиковыйБуфер = Окр(СпросВМесяц * (МаксимальныйИндексСезонности - 1), 2)

Для хвостовых категорий:
Min = 0
Target = 0
Max = 0

Для нормируемых категорий:
Min = Окр(СпросВДень * (СрокПоставкиДней + СтраховойЗапасДней), 2)
Target = Окр(СпросВДень * (СрокПоставкиДней + ПериодПополненияДней + СтраховойЗапасДней) + ПиковыйБуфер, 2)
Max = Окр(Target + МинимальнаяПартия + БуферПоставки, 2)
```

`СтраховойЗапасДней` больше не считается напрямую из максимального индекса сезонности. Пик спроса выделен в `ПиковыйБуфер`, чтобы не превращать редкий сезонный всплеск в постоянный минимальный запас.

Категории класса `Хвост` не нормируются автоматически: они остаются диагностикой для классификации, разовой закупки или исключения.

`МинимальнаяПартия` пока берется как средняя партия поставки, `БуферПоставки` как разница между максимальной и средней партией. Для сезонных категорий это только черновик: потребуется календарь закупочного окна.

## 15. Вариант `КонтрольНормы`

Это управленческий слой: он соединяет текущие остатки из `ПокрытиеФакт` и расчетный коридор из `БазаНормы`.

Выбранные поля:

Для компактного варианта без детальных записей:

- убрать группировки `СтатусКоридораНормы` и `ТипПолитики`;
- оставить структуру `КонтурБизнеса -> ТипЕдиницыКонтроля -> КатегорияНормы`;
- `РекомендацияНормы` добавить в ресурсы как `Максимум(РекомендацияНормы)` и вывести в выбранных полях группировки `КатегорияНормы`;
- детальные записи выключить;
- `СтатусКоридораНормы` и `ПериодНормы` не выводить как детальные поля.

Логика статуса:

```text
Не нормируется -> хвостовая категория
Нет нормы -> целевая норма не рассчитана

```

Для статусов `Не нормируется` и `Нет нормы` отклонения от цели, дефицит и избыток заполняются нулями: эти строки нельзя смешивать с нормируемой потребностью.

Для денежного сравнения используются `ОстатокРубКонтроль`, `НормаМинРубКонтроль`, `НормаЦельРубКонтроль`, `НормаМаксРубКонтроль`, `ОтклонениеОтЦелиРуб`, `ПокрытиеЦелиРубНормы`.

`ПокрытиеЦелиНормы` на верхнем итоге при смешении кг и усл. ед. лучше скрывать. Для верхнего итога используем `ПокрытиеЦелиРубНормы`.

Этот вариант уже можно использовать как прототип будущего блока закупок в виджете: он отвечает не просто "сколько лежит", а "что с этим делать".

## 16. Вариант `КонтрольКонтура`

Это верхний слой для будущего виджета. Он не показывает категории, а дает одну строку по контуру бизнеса: отдельно рубли, кг и усл. ед., плюс текстовую рекомендацию по комбинации факторов.

Важно: остатки контура считаются по всем категориям, включая `Нет нормы` и `Не нормируется`, чтобы сумма совпадала с общим складским остатком. Норма и покрытие считаются только по категориям, для которых норма реально рассчитана. Поэтому счетчики категорий без нормы нужно смотреть рядом с покрытием: они объясняют, какая часть остатка пока не участвует в нормативной модели.

### 16.3. Как оформить вариант отчета

Отбор:


Структура:

```text
  КонтурБизнеса
```

Выбранные поля:

```text

ОтклонениеОтЦелиРуб
ПокрытиеЦелиРубНормы
ОстатокКгКонтура
НормаЦельКгКонтура
ОтклонениеКгКонтура
ПокрытиеКгКонтура
ОстатокУслЕдКонтура
НормаЦельУслЕдКонтура
ОтклонениеУслЕдКонтура
ПокрытиеУслЕдКонтура
СтатусРубКонтура
СтатусКгКонтура
СтатусУслЕдКонтура
РекомендацияКонтура
КатегорийДефицит
КатегорийНижеЦели
КатегорийИзбыток
КатегорийНетНормы
КатегорийНеНормируется
```

Детальные записи для этого варианта не нужны. Если включить детальные записи, отчет начнет показывать служебную строку слоя, а не компактный вид для виджета.

Интерпретация:

```text
Рубли ниже цели + физика ниже цели -> общий дефицит
Рубли ниже цели + физика выше цели -> структурный перекос: много массы, мало нужной стоимости/ассортимента
Рубли выше цели + физика ниже цели -> дорогой запас при физическом дефиците
Рубли выше цели + физика выше цели -> профицит
Рубли в норме + одна физика ниже, другая выше -> физический перекос
```

Категории без нормы не участвуют в сумме нормы контура, но их остатки входят в общий остаток контура. Это сделано сознательно: директор должен видеть весь складской остаток, а методологический долг показывается счетчиками `КатегорийНетНормы` и `КатегорийНеНормируется`.

Итоговую строку СКД по всем контурам лучше не использовать для текстовых статусов и рекомендаций: строковые ресурсы агрегируются через `Максимум(...)`, поэтому общий итог может выбрать один из текстов, а не рассчитать новую управленческую рекомендацию. Для виджета и контроля смотреть строки `Финист` и `Юниант`.

Чтобы скрыть строку `Итого` в варианте `КонтрольКонтура`:

1. Открыть вариант `КонтрольКонтура` на вкладке `Настройки`.
2. Выделить самый верхний узел `Отчет`.
3. Перейти в нижнюю вкладку `Другие настройки`.
4. Найти настройки общих итогов и поставить:
   - `Расположение общих итогов по вертикали` = `Нет`;
   - `Расположение общих итогов по горизонтали` = `Нет`, если поле есть.
5. Если в конкретной версии платформы этих полей нет, искать близкую настройку `Выводить общий итог` / `Выводить итоги` и поставить `Нет`.

Строки `Финист` и `Юниант` останутся, исчезнет только общий итог по отчету.

## 17. Что сверять после запуска

Первый контроль:

```text
Контур Юниант: ОстатокРуб и ОстатокКг
Контур Финист: ОстатокРуб и ОстатокКг
Эрион: должен быть отдельным контуром, не смешанным с Юниантом/Финистом
СтрокБезЦены: должны быть видны, а не исчезать из отчета
```

Ожидаемо, рубли могут отличаться от текущего виджета, потому что экспериментальный отчет использует взвешенную цену и не отбрасывает физические строки без цены.
