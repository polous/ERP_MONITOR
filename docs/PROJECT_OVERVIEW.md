# ERP_MONITOR: описание работ и принципов

## Цель проекта

Мы делаем монитор бизнес-метрик для директора в 1С ERP. Это отдельное расширение `ERP_MONITOR` со своей обработкой `MON_МониторРуководителя`, виджетами на форме и связанными отчетами СКД, которые открываются по клику на заголовки/группы виджетов.

Монитор нужен не как обычный отчет, а как управленческая панель: на первом экране должны быть видны проблемные зоны и ключевые проценты/суммы, а детализация открывается отдельно в отчетах.

## Ограничение среды

1С запускается через удаленный стол. У нас нет прямого доступа к объектам расширения, формам, СКД и модулям из репозитория.

Поэтому рабочая схема такая:

1. Код и запросы выгружаются из 1С в `.txt` файлы.
2. Изменения сначала готовятся в этих `.txt` файлах.
3. Пользователь вручную переносит готовые фрагменты обратно в конфигуратор 1С.
4. Результат проверяется в 1С, при необходимости в репозиторий добавляется новый лог/выгрузка.

Важно: не считать репозиторий полной выгрузкой расширения. Это рабочая копия логики, запросов и диагностик.

## Текущие файлы проекта

- `МОДУЛЬ_ОБРАБОТКИ.txt` - основной код обработки/формы `MON_МониторРуководителя`. Здесь пересчитываются виджеты и открываются связанные отчеты.
- `МОДУЛЬ_ОБЪЕКТА_ОТЧЕТА_ПРОДАЖ.txt` - модуль объекта отчета `MON_МониторПродаж`. Отчет строит внешний набор данных программно и отдает его в СКД.
- `СКД.txt` - сохраненные фрагменты запросов СКД. Сейчас видны наборы для остатков/закупок: остатки, закупки, себестоимость, стоимость остатка.
- `ЛОГ.txt` - диагностический текст по закупкам: факт, нормы, остатки, расшифровки по организациям, складам, классам документов и категориям.
- `*.xls`, `*.xlsx` - Excel-файлы для сверки исходных данных и расчетов.

## Главная обработка `MON_МониторРуководителя`

Файл: `МОДУЛЬ_ОБРАБОТКИ.txt`.

Основной сценарий:

- `ПриОткрытии` задает `ДатаОтчета` и вызывает обновление всех виджетов.
- `ДатаОтчетаПриИзменении` пересчитывает все виджеты при смене даты.
- Для открытия детализаций используются отдельные процедуры, которые готовят параметры СКД и вызывают `ОткрытьФорму(...)`.

Сейчас при открытии/смене даты вызываются:

- `ОбновитьВиджетСветофорSKU()`
- `ОбновитьВиджетСкладаНаСервере()`
- `ОбновитьВиджетПродажНаСервере()`
- `ОбновитьВиджетЗакупокНаСервере()`

Есть старая версия складского расчета `ОбновитьВиджетСкладаНаСервере_старая()`. Ее не использовать как актуальную без отдельной причины.

## Виджет складов / SKU

Задача виджета - показать здоровье складских остатков:

- дефицит;
- риск;
- норма;
- затовар;
- сроки годности: тухляк, распродажа, внимание, свежак;
- деньги в затоваре и упущенную маржу по дефициту;
- анти-топы неликвида и распродажи;
- проблемные склады.

Текущая логика:

- Для `MON_СветофорSKU_ПланФакт` используется СКД, результат выгружается в `ТаблицаЗначений`.
- Для складского виджета актуальная процедура `ОбновитьВиджетСкладаНаСервере()` делает пакетный запрос по планам, продажам, себестоимости и остаткам.
- Расчет опирается на дату отчета, период анализа продаж, планы продаж и остатки на дату актуальности.
- Визуальные элементы формы заполняются через `Элементы.Дец_*` и фоновые элементы.

Связанная детализация:

- клик по SKU открывает `Отчет.MON_СветофорSKU_ПланФакт.Форма`;
- клик по складу открывает `Отчет.MON_ДетализацияСклада.Форма`;
- параметры отчета готовятся через `УстановитьПараметрНадежно` или компоновщик настроек.

## Виджет продаж

Задача виджета - дать директору срез по выполнению продаж и маржинальности.

Основные процедуры в `МОДУЛЬ_ОБРАБОТКИ.txt`:

- `ОбновитьВиджетПродажНаСервере()` - считает агрегаты для виджета.
- `ЗапросПланПродажВиджета()` - план продаж в рублях.
- `ЗапросФактПродажВиджета()` - факт продаж, себестоимость, валовая прибыль.
- `ЗапросЛогистикаФактВиджета()` - логистика для корректировки маржинальности.
- `ПолучитьПорогиМаржиПоОтделам()` - пороги окраски маржи по отделам.
- `ОпределитьКлючОтдела()` и `ПолучитьМассивЦелевыхПодразделений()` - нормализация подразделений для строк виджета.

Связанная детализация:

- `ОткрытьОтчетПоПродажам()` открывает `Отчет.MON_МониторПродаж.Форма`;
- `ПодготовитьНастройкиПродаж()` передает в СКД параметр `ДатаОтчета` и пользовательские настройки.

## Отчет `MON_МониторПродаж`

Файл: `МОДУЛЬ_ОБЪЕКТА_ОТЧЕТА_ПРОДАЖ.txt`.

Это отчет с программным формированием данных:

- `ПриКомпоновкеРезультата` отключает стандартную обработку;
- получает параметр `ДатаОтчета`;
- вызывает `СформироватьДанные(ДатаОтчета)`;
- передает результат как внешний набор данных `МониторПродаж`;
- дальше результат выводится через стандартный процессор компоновки СКД.

Расчет данных:

- строится дерево `Подразделение -> Менеджер`;
- подтягиваются планы в рублях и килограммах;
- считается факт продаж, себестоимость, валовая прибыль;
- отдельно учитывается логистика;
- считаются АКБ, новые клиенты, новые сетевые позиции и ПДЗ.

Важная договоренность: имя внешнего набора данных в СКД должно совпадать с `"МониторПродаж"`.

## Виджет закупок

Задача виджета - сравнить фактические остатки закупаемых категорий с нормой и показать отклонение в рублях и условных единицах.

Основная процедура:

- `ОбновитьВиджетЗакупокНаСервере()`.

Опорные функции:

- `ПолучитьСкладыЗакупокПоДатеОтчета()` - список складов остатков, с исключением исторических складов для дат 2026+.
- `ПолучитьСкладыРасходаЗакупокПоДатеОтчета()` - склады расхода для нормы.
- `ЗапросОстаткиЗакупокВиджета()` - остатки и стоимость остатков.
- `ЗапросРасходКгЗакупокВиджета()` - расход по закупочным видам номенклатуры.
- `НакопитьТаруПроизводственногоРасхода()` - дополнительный учет тары по производственному расходу.
- `РассчитатьИтогиНормПоОрганизациям()` и связанные функции норм - расчет норм по организациям и категориям.
- `ПолучитьВидыНоменклатурыЗакупокПоУмолчанию()` и `ПолучитьСкладыЗакупокПоУмолчанию()` - основные справочники фильтров.

Цвета закупок:

- `ПолучитьЦветПоОтклонениюОтНормы()` - окраска по отношению факта к норме.
- `ПолучитьЦветПоДиапазонуНормы()` - более гибкая окраска по диапазону.

Диагностика:

- `СформироватьТекстНормПоОрганизациям()`;
- `СформироватьТекстДиагностикиСрезанныхКатегорий()`;
- `СформироватьТекстДиагностикиРасходаПоРегистраторам()`;
- `СформироватьТекстДиагностикиФинистРасходПоВсемСкладам()`;
- `СформироватьТекстДиагностикиКонтрагентовЗакупок()`;
- `СформироватьТекстДиагностикиТарыПоТипамДокументов()`;
- `СформироватьТекстДиагностикиКальмаров()`.

Диагностический вывод сохраняется в `ЛОГ.txt` для разбора расхождений.

## СКД и отчеты

В проекте есть два подхода:

1. Классический СКД-запрос в схеме компоновки данных.
2. Программное формирование внешнего набора данных в модуле объекта отчета.

Пример второго подхода - `MON_МониторПродаж`: модуль объекта формирует `ТаблицаЗначений`, а СКД отвечает за структуру, группировки, оформление и вывод.

При изменениях нужно всегда проверять три вещи:

- имя отчета/обработки в коде совпадает с именем объекта расширения;
- параметры СКД имеют те же имена, что используются в коде (`ДатаОтчета` и т.п.);
- имена внешних наборов данных совпадают между модулем объекта и СКД.

## Дата отчета

`ДатаОтчета` - главный параметр пересчета. Сейчас в `ПриОткрытии` явно задано значение `'20250630'`.

Большинство расчетов используют:

- начало и конец месяца даты отчета для продаж;
- дату актуальности/среза остатков;
- историю продаж/расхода для расчета норм и обеспеченности.

При будущих изменениях надо отдельно фиксировать, какая дата используется:

- дата отчета на форме;
- период продаж;
- дата среза остатков;
- период расхода для нормы;
- период закупок/себестоимости.

## Правила дальнейшей работы

1. Перед изменением читать `README.md` и этот файл.
2. Работать с `.txt` как с источниками правды для переносимых изменений.
3. Не переименовывать элементы формы, отчеты, параметры СКД и внешние наборы без явного указания.
4. Для новых виджетов повторять существующий паттерн: расчет на сервере, заполнение `Дец_*`/`Фон_*`, отдельная процедура открытия детализации.
5. Если нужен новый отчет-детализация, сразу описывать:
   - имя объекта отчета;
   - имя формы;
   - параметры СКД;
   - нужен ли классический СКД-запрос или внешний набор данных из модуля объекта.
6. После правок в коде давать пользователю точный список фрагментов, которые нужно перенести в 1С.
7. Логи диагностики хранить отдельно, чтобы можно было сравнивать расчет до/после.

## Текущий статус

- Складской/SKU блок уже реализован и имеет детализации.
- Продажный блок реализован как виджет плюс отдельный отчет `MON_МониторПродаж` с модулем объекта.
- Закупочный блок частично реализован: есть расчет остатков, норм, цветов и большой диагностический контур; требуется дальнейшая доводка по бизнес-правилам и сверкам.

## Что считать результатом работы

Результат каждой итерации - не только измененный код, но и переносимый комплект:

- какие строки/процедуры в `.txt` изменены;
- в какой объект 1С их переносить;
- какие параметры/элементы формы/настройки СКД должны существовать;
- как проверить результат на форме монитора или в связанном отчете.
