# Экспериментальная аналитика закупок

Дата фиксации: 2026-05-25.

## Решение по форме эксперимента

Текущий виджет закупок оставляем как рабочий управленческий индикатор. Новую методологию не надо сразу вшивать в этот виджет: сначала делаем отдельный детальный отчет, а уже после проверки сворачиваем его в новый компактный виджет.

Рекомендуемый объект 1С:

```text
Отчет.MON_МониторЗакупокЭксперимент
```

Текст модуля объекта отчета хранится в файле:

```text
МОДУЛЬ_ОБЪЕКТА_ОТЧЕТА_ЗАКУПОК_ЭКСПЕРИМЕНТ.txt
```

В СКД внешний набор должен ссылаться на объект данных:

```text
МониторЗакупок
```

Пошаговая ручная настройка СКД описана в:

```text
docs/PURCHASE_EXPERIMENT_SCD_SETUP.md
```

Почему отчет, а не виджет:

- виджет слишком мал для проверки методологии;
- спорные места нужно видеть построчно: организация, склад, контрагент, номенклатура, категория, источник спроса, статус;
- по отчету можно сверяться с Excel и логом без постоянной правки формы;
- когда модель станет устойчивой, виджет будет брать уже готовые агрегаты из этой же расчетной таблицы.

## Базовый принцип

Остатки - первая и обязательная база расчета. Именно на них уже смотрит директор при разговоре с закупками, поэтому экспериментальный отчет должен начинаться не с нормы, а с текущей картины запасов.

Сначала строим каноническую таблицу остатков:

```text

КонтурБизнеса
ОрганизацияУчета

Склад

Номенклатура
Артикул

ЕдиницаХранения

```

Только после этого к остаткам присоединяются спрос, норма, отклонение и рекомендация.

## Почему остатки нельзя отбрасывать

В текущем виджете стоимость остатка зависит от найденной цены. Это удобно для рублевой суммы, но опасно для физики склада: строка без цены не должна исчезать из кг.

Правило новой модели:

```text
Физический остаток считается всегда.
Рублевый остаток считается, если есть цена.
Строки без цены попадают в отдельную диагностику "нет цены".
```

Так директор видит реальную загрузку склада, а не только оцененный деньгами кусок.

## Контуры бизнеса

Эрион нельзя решать строковыми фильтрами внутри каждого запроса. Нужна явная классификация контура.

Минимальный классификатор:

```text
Организация / Склад / Контрагент / Заказ -> КонтурБизнеса
```

Контуры:

```text
Юниант
Финист
Эрион
Неопределено
```

Правила:

- `Юниант` и `Финист` участвуют в нашей норме;
- `Эрион` показывается в диагностике и отдельной группе, но не смешивается с нормой Юнианта/Финиста;
- `Неопределено` не должно молча превращаться в Юниант, оно должно попадать в диагностику.

## Слои расчета

### 1. Остатки

Источник для первой версии:

```text
РегистрНакопления.ТоварыОрганизаций.Остатки(...)
```

Причина: этот регистр уже используется в текущем виджете и ближе к управленческой картине остатков по организациям.

Нужно сохранить сопоставимость с текущим виджетом:

- те же даты среза;
- те же склады;
- те же организации;
- отдельно показывать строки, которые текущий виджет отбрасывает из-за цены.

### 2. Цена

Цена нужна отдельно от физического остатка.

Приоритет:

```text
1. Взвешенная средняя по приходу: СуммаСтоимость / СуммаКоличество
2. Последняя закупочная цена
3. Средняя цена по категории
4. Нет цены -> диагностика
```

Нельзя использовать простое среднее цен партий, если есть возможность считать взвешенно.

### 3. Спрос

Единый источник спроса невозможен для всех категорий. Нужен тип спроса.

```text
Категория              Источник спроса
Регулярное сырье       производственный расход или план производства
Рыба/морепродукты      план продаж/производства ГП через нормы выхода
Тара/упаковка          план выпуска или производственный расход
Ингредиенты            производственный расход, затем рецептуры
Новые позиции          ручной минимальный уровень до накопления истории
Эрион                  отдельный контур, не наша норма
```

### 4. Норма

Коэффициент заменяется на параметры процесса:

```text
СрокПоставкиДней
ПериодМеждуЗакупкамиДней
ОкноЗакупки
СтраховойЗапасДней
МинимальнаяПартия
КратностьПартии
СрокГодностиДней
ЛимитСкладаКг
```

Формулы:

```text
Мин = СпросВДень * (СрокПоставкиДней + СтраховойЗапасДней)

Цель = СпросВДень * (СрокПоставкиДней + ПериодМеждуЗакупкамиДней + СтраховойЗапасДней)

Макс = Цель + МинимальнаяПартия
```

Для сезонной закупки:

```text
Цель = ПрогнозСпросаДоСледующегоОкнаЗакупки + СтраховойЗапас
Макс = Цель + ДопустимыйПартийныйБуфер
```

Так большая норма по кальмару объясняется не коэффициентом 9, а календарем закупки, прогнозом потребления и партийностью.

## Что показывать директору

В будущем виджете показывать не только две суммы, а три смысловых блока:

```text
Остатки
факт руб / факт кг

Риск закупки
дефицит до цели руб / кг
количество дефицитных групп

Избыток
избыток сверх максимума руб / кг
количество избыточных групп
```

Так не смешиваются две разные управленческие задачи:

- где надо купить;
- где надо остановиться или перераспределить.

## План внедрения

1. Создать отчет `MON_МониторЗакупокЭксперимент`.
2. Первым этапом вывести только канонические остатки.
3. Сверить суммы остатков с текущим виджетом по Юнианту и Финисту.
4. Добавить цену и диагностику строк без цены.
5. Добавить классификацию контура бизнеса.
6. Добавить спрос по текущим источникам, но с явным полем `ИсточникСпроса`.
7. Добавить расчет min/target/max через параметры процесса.
8. Добавить reconciliation-блок с Excel.
9. После проверки сделать новый компактный виджет на базе итогов отчета.

## Ключевое решение после сверки остатков

Сверка на `30.06.2025` показала, что канонические остатки достаточно надежны для дальнейшей модели:

```text
Физический остаток, кг:     980 286,88
Остаток с ценой, кг:        948 027,884
Остаток без цены, кг:        32 259
Остаток руб, взвешенная цена: 174 837 373,81
Остаток руб, метод виджета:   176 921 753,24
```

Вывод:

- физические кг считаются корректно;
- текущий виджет скрывал кг без цены;
- рубли находятся в допустимой зоне сверки с Excel за июнь/июль;
- дальше нельзя тратить основной ресурс на подгонку Excel или старого виджета;
- следующий этап - расчет физического спроса и нормы из бизнес-процесса.

## Следующий этап: `СпросФизический`

Норма закупок не должна считаться от коэффициентов закупщиков. Следующий слой отчета должен формировать таблицу физического спроса:

```text
ДатаНач
ДатаКон
КонтурБизнеса
ОрганизацияНормы
КатегорияНормы
ИсточникСпроса
НоменклатураСырья
НоменклатураГП
Склад
Документ
КоличествоСпросКг
КоличествоСпросУслЕд
КоэффициентВыхода
ТипСпроса
КачествоСпроса
ПричинаВключения
ПричинаИсключения
```

`СпросФизический` должен быть не одним запросом, а объединением нескольких источников с одинаковым выходным форматом.

### Источники спроса по приоритету

1. `План производства / план продаж ГП -> рецептуры -> сырье`

Идеальный источник для будущей модели. Он отвечает на вопрос, сколько сырья нужно для будущего выпуска.

Если в тестовой базе нет нормального плана или рецептур, источник остается в модели как целевой, но временно помечается статусом:

```text
Источник недоступен
```

2. `Фактический выпуск / производственный расход`

Базовый источник для регулярного сырья, ингредиентов и тары, пока нет полноценного планового слоя.

Он отвечает не "сколько закупали", а "сколько реально потреблял процесс".

3. `Закупки у поставщиков`

Допустимы только как proxy-источник для категорий, где производственный расход и рецептуры не дают устойчивой картины.

Это не физика потребления, а физика пополнения. Поэтому такие строки должны иметь отдельный `ИсточникСпроса = ЗакупкиПоставщиков`.

4. `Ручной прогноз / сезонное окно`

Разрешен только как явная политика категории, а не как скрытый коэффициент.

Пример: кальмар.

```text
Причина большого запаса = сезонное окно закупки + прогноз потребления до следующего окна + партия + риск поставки
```

а не:

```text
коэффициент = 9
```

## Политики категорий вместо коэффициентов

Следующий справочник/таблица настроек должен описывать не коэффициенты, а бизнес-параметры процесса:

```text
ОрганизацияНормы
КатегорияНормы
КонтурБизнеса
ЕдиницаКонтроля
ИсточникСпросаОсновной
ИсточникСпросаРезервный
СрокПоставкиДней
ПериодМеждуЗакупкамиДней
ЧастотаПересмотраДней
СтраховойЗапасДней
МинимальнаяПартия
КратностьПартии
БуферПоставки
СезонноеОкноНачало
СезонноеОкноКонец
ГоризонтДоСледующегоОкнаДней
СрокГодностиДней
ЛимитСкладаКг
ПравилоЦены
ПравилоВключения
ПравилоИсключения
```

Эта таблица все еще является настройкой, но каждое значение защищается бизнес-логикой:

- срок поставки берется из процесса закупки;
- период между закупками - из практики пополнения;
- страховой запас - из волатильности спроса/срыва поставки;
- сезонное окно - из календаря доступности сырья;
- минимальная партия - из условий поставщика;
- лимит склада - из физической емкости.

## Формула нормы из физики процесса

В тестовой базе дата отчета и окно нормы разделены:

```text
Дата отчета -> срез остатков
Референс с 2025-01 по последний закрытый месяц данных -> спрос, сезонность, будущая норма
```

Это нужно потому, что 2024 год в базе неполный и шумный, а дата отчета не должна менять нормативную историю. Отчет на любой месяц 2025 или 2026 показывает остатки на выбранную дату, но нормативный спрос считает по общей доступной истории начиная с `01.01.2025`.

Если в базе последние движения спроса есть, например, `13.04.2026`, то апрель считается неполным и не включается в норму. Референсное окно становится `01.01.2025-31.03.2026`. Когда база обновится до полного апреля, окно автоматически расширится до `30.04.2026`.

Для несезонных категорий:

```text
СпросВДень = ПрогнозПотребленияЗаПериод / ДнейВПериоде

Min =
    СпросВДень * СрокПоставкиДней
    + СпросВДень * СтраховойЗапасДней

Target =
    СпросВДень * (СрокПоставкиДней + ПериодМеждуЗакупкамиДней)
    + СпросВДень * СтраховойЗапасДней

Max =
    Target
    + МинимальнаяПартия
    + БуферПоставки
```

Для сезонных категорий:

```text
Target =
    ПрогнозПотребленияДоСледующегоОкнаЗакупки
    + СтраховойЗапас

Max =
    Target
    + ДопустимыйПартийныйБуфер
```

Ограничения:

```text
Max <= ЛимитСкладаКг
Target <= ПотребностьДоИстеченияСрокаГодности
```

Если ограничение нарушено, отчет должен показывать не "норму", а конфликт:

```text
Потребность выше складского лимита
Потребность выше срока годности
Минимальная партия больше допустимого максимума
```

## Практический следующий шаг в `MON_МониторЗакупокЭксперимент`

После слоя остатков добавляем не финальную норму, а диагностический слой спроса:

```text
Вариант отчета: СпросФизический
```

Первый источник для реализации:

```text
производственный расход / движение со складов за 12 месяцев
```

Почему именно он:

- он ближе к физике потребления, чем закупки у поставщиков;
- он позволит сразу увидеть тары/упаковку, ингредиенты, сырье;
- он покажет, где закупки не равны потреблению;
- он не требует ждать полноценных планов 2026 и рецептурной модели.

Параллельно оставляем колонку `ИсточникСпроса`, чтобы не смешать разные природы спроса:

```text
ПроизводственныйРасход
ЗакупкиПоставщиков
ПланГПЧерезРецептуры
РучнойСезонныйПрогноз
НетИсточника
```

Только после этого строится `НормаФизическая`.

Реализация от 2026-05-26:

- в модуль объекта отчета добавлено поле `СлойДанных`;
- строки остатков помечаются как `Остатки`;
- строки физического спроса помечаются как `СпросФизический`;
- первый источник спроса - производственный расход из `РегистрНакопления.ТоварыНаСкладах.Обороты`;
- период спроса - 12 месяцев, заканчивающихся месяцем `ДатаОтчета`;
- складовой контур спроса берется из отдельного списка производственных/расходных складов;
- документальные типы первого этапа: `ДвижениеПродукцииИМатериалов`, `РасходныйОрдерНаТовары`, `ПроизводствоБезЗаказа`, `ВнутреннееПотребление`.

Ограничение первого этапа: это не плановый спрос через рецептуры. Это фактический физический расход, нужный как переходная опора для проверки категорий, складов и масштаба потребления.

Выводы:

- слой спроса технически работает и дает физически читаемые месяцы потребления;
- Финист по физическому кг близок к одному месяцу покрытия;
- Юниант по кг имеет около двух месяцев покрытия;
- материалы/тара/упаковка особенно у Юнианта выглядят запасенными относительно фактического производственного расхода;
- следующий аналитический слой должен быть не финальной нормой, а `ПокрытиеФакт`: остаток / фактический спрос в месяц по каждой категории.

Реализация следующего шага:

- в модуль добавлен синтетический слой `ПокрытиеФакт`;
- он агрегирует строки `Остатки` и `СпросФизический` по ключу `КонтурБизнеса + ОрганизацияНормы + ТипЕдиницыКонтроля + КатегорияНормы`;
- считает `ПокрытиеМесКг`, `ПокрытиеМесУслЕд`, `ПокрытиеМес`;
- присваивает первичный статус покрытия: `Нет остатка при спросе`, `Меньше 1 месяца`, `1-2 месяца`, `2-4 месяца`, `Больше 4 месяцев`, `Есть остаток, нет спроса`.

Этот статус еще не является закупочной рекомендацией. Это диагностический показатель обеспеченности от фактического спроса, который нужен перед вводом политик категорий.

Проверка `ПокрытиеФакт-2.html` показала техническую ошибку первой настройки: ресурс покрытия нельзя агрегировать через `Максимум(...)`, потому что на уровне организации он показывает максимальное покрытие одной категории. Покрытие верхнего уровня должно считаться только как:

```text
Сумма(Остаток) / Сумма(СпросВМесяц)
```

Для этого в строках слоя `ПокрытиеФакт` дополнительно заполняются технические поля `КоличествоКг`, `КоличествоУслЕд`, `СтоимостьРуб`, чтобы существующие ресурсы остатков корректно работали и в синтетическом слое.

Повторная проверка после исправления показала корректную верхнюю математику:

```text
Финист кг:       223 120,50 / 230 956,80 = 0,97 мес
Финист усл. ед.: 772 683,79 / 685 870,85 = 1,13 мес

Юниант кг:       757 166,38 / 365 239,42 = 2,07 мес
Юниант усл. ед.: 4 751 022,41 / 964 835,82 = 4,92 мес

Итого кг:        980 286,88 / 596 196,22 = 1,64 мес
Итого усл. ед.:  5 523 706,21 / 1 650 706,66 = 3,35 мес
```

Ключевой вывод: `ПокрытиеФакт` готов как диагностический слой, но он не является нормой. Нельзя автоматически объявлять категорию хорошей или плохой только по месяцам покрытия без политики категории.

Примеры:

- `Юниант / Морепродукты: кальмары` имеет покрытие около `0,21 мес`, но для сезонной закупки это может быть критическим дефицитом или нормальным моментом до окна закупки - зависит от календаря закупки.
- `Юниант / Морепродукты: креветки` имеет покрытие около `36 мес`; это может быть избыток, но также может быть следствием нерегулярного спроса, ошибочной классификации или отсутствия корректного источника спроса.
- `Финист / Морепродукты` имеет высокое покрытие, но категория слишком укрупнена для управленческого решения.
- `Финист / Рыба` и `Финист / Субпродукт (из рыбы и морепродуктов)` показывают спрос без остатка; это важно для закупки, но требует проверки, не лежит ли запас в другой категории или на другом контуре.

Следующий слой: `ПолитикиКатегорий`. Он должен описать, какое покрытие считается нормой для каждой категории не через магический коэффициент, а через физические параметры процесса.

Реализация от 2026-05-26:

- добавлен синтетический слой `ПолитикиКатегорий`;
- он строится из строк `ПокрытиеФакт`, поэтому в нем уже видны остаток, спрос, покрытие и статус покрытия;
- для каждой категории задается черновой `ТипПолитики`: `Обычная`, `Партийная`, `Сезонная`, `Партийная/сезонная`, `Проверить`;
- числовые параметры политики пока специально равны `0`;
- `СтатусПолитики` остается `Требует решения` или `Требует классификации`.

Важно: этот слой не должен молча превращаться в норму. Он нужен, чтобы пройти по категориям и заполнить реальные бизнес-параметры: срок поставки, частоту закупки, страховой запас, минимальную партию, сезонное окно, срок годности, складской лимит.
